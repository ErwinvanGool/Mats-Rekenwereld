### Rubric Scores

#### Category 1: Parent Gate

1. **Is the parent gate effective at keeping a 6-year-old out?** 3/5
   The 4-digit PIN keypad is a solid gate — a child cannot guess or accidentally enter a valid 4-digit sequence. However, the default PIN is still `1234` (`state.js` `defaultSettings()` line ~57), which is trivially guessable. The 🔒 trigger button is in the persistent sticky header on every game screen — prominent and visible to a curious child. No automatic PIN-reset on first boot.

2. **Is the parent gate easy for an adult to pass through quickly?** 4/5
   Large 80×80 px keypad buttons, clear OK (purple, distinct), large dot display. A parent who knows the PIN completes entry in 4–5 taps. Minor deduction: default `1234` makes the gate feel symbolic on a fresh install.

3. **Is it visually clear where the parent gate trigger is?** 4/5
   The 🔒 emoji button is placed at the right edge of the orange sticky header across all game screens. There is also a "🔒 Ouders" text button in the start screen footer (`.start-screen__parent-link`, which has CSS). The header button has no dedicated CSS class style (`.app-header__parent-btn` is referenced in HTML but not defined in `styles.css`), so it inherits only the base `button {}` reset — no border, no background, no sizing. On the orange header the emoji is still legible, so a parent can find it.

4. **Does the parent gate close properly and return to the game cleanly?** 4/5
   Both `screen-parent` and `screen-parent-panel` have a `nav-back` button hard-coded to `data-nav="screen-worldmap"`. Navigation uses the same `fadeSlideIn` animation as every other screen. Minor deduction: closing always goes to the world map, not to wherever the parent was before entering settings.

#### Category 2: Clarity and Usability

5. **Are all settings clearly labeled and easy to understand?** 3/5
   Section headings (`Oefeningen`, `Geluid`, `Beheer`, `Badges verdiend`) are generated as plain `<h3>` tags with no CSS class — they render in the browser's default heading style, not the game's Nunito font stack. Individual operation dropdowns now show descriptive labels from `data.js` (`l.description`): "Tot 10", "Tot 20", "Tot 40", "Tafels 1–2", etc. — which is genuinely informative. However, the section title "Oefeningen" gives no hint that it contains toggle + level-select pairs; a parent new to the UI may not immediately understand the relationship between the checkbox and the dropdown on the same row.

6. **Can the parent see the current value of each setting at a glance?** 4/5
   Checkboxes are pre-checked from state. Dropdowns have the correct `selected` option pre-rendered. The sound checkbox reflects `state.settings.soundEnabled`. Deducted one point because the panel shows no snapshot of the child's current state (level, blocks, streak).

7. **Are the controls appropriate for each setting type?** 3/5
   Checkboxes for enabling/disabling operations: appropriate. Dropdowns for level: appropriate. Reset/PIN as buttons: appropriate. The sound setting is rendered as a bare `<input type="checkbox" data-sound-toggle>` without the `.toggle` CSS wrapper. The full toggle-switch component (`.toggle`, `.toggle__track`, thumb animation) is defined in `styles.css` but never applied here. `renderParentPanel()` in `main.js` line ~898 renders the checkbox without the wrapper.

8. **Is the settings panel organized in a logical order?** 3/5
   Ordering (Operations → Sound → Management → Badges) is sensible. However, there are no grouping containers (`.settings-group` cards) between the `<h3>` headings and the rows — the HTML comment inside `parent-panel__body` shows the intended `<section class="settings-group">` wrapper but it is never generated by `renderParentPanel()`. The "Beheer" section puts reset (destructive) and PIN change (security) adjacent with no visual separation.

9. **Can a parent complete all settings changes in under 30 seconds?** 4/5
   Everything is on one scrollable panel. No nested tabs or sub-screens. Deducted one point: changing the PIN requires `window.prompt()` — a separate browser dialog — which breaks the native-app feel and cannot be dismissed with an in-game button.

10. **Is the settings panel usable on iPad in landscape mode?** 3/5
    The CSS block `.parent-panel` (white card, max-width 760 px, box-shadow, purple border) is defined in `styles.css` (line ~1620) but the section element uses `class="screen screen--parent-panel"` (`index.html` line 564), not `class="parent-panel"`. The card container styles are never applied. Individual `.parent-setting` rows and `.btn` buttons are large enough for touch. The `data-settings-content` wrapper has class `parent-panel__body`, which also has no CSS rule. The panel renders as a plain flex column on the app background with no card distinction.

#### Category 3: Completeness

11. **Are all expected settings present?** 2/5
    Present: enable/disable per operation (4 ops), level per operation (3 levels each with descriptive text), sound on/off, reset progress, change PIN.
    **Missing:** explicit max-number range control; problem type selector (numeric symbols vs. visual icon counting vs. mixed). Both are listed as required in the copilot instructions. A parent cannot force visual-counting mode or cap difficulty to, e.g., single-digit sums only.

12. **Can the parent view the child's progress?** 1/5
    The parent panel renders only a badge list. `state.progress.totalCorrect`, `bestStreak`, `earnedBlocks`, `earnedStickers`, and `state.builds.completedBuilds` all exist in state and are fully rendered on the child-facing `screen-progress` — but none of this data is surfaced inside the parent panel. A parent reviewing settings has no quick snapshot of how the child is doing without exiting the panel and navigating to the child screen.

13. **Is there a reset progress option with a safety confirmation?** 3/5
    "Voortgang wissen" triggers `window.confirm('Weet je zeker dat je alle voortgang wilt wissen?')` followed by `window.alert('Voortgang gewist.')` — a working two-step confirmation. The `resetProgress()` function correctly clears all progress and build state while preserving settings (`parent-settings.js` line ~100). Score kept at 3/5 because the native browser dialogs are jarring and potentially child-visible, and the panel does not re-render after reset (the badge list remains stale until the parent navigates away and back).

14. **Can the parent adjust settings as the child improves over time?** 4/5
    Per-operation level dropdowns with three descriptive tiers ("Tot 10 / Tot 20 / Tot 40" for addition) allow progressive tuning without resetting progress. Switching operations on/off also works without data loss. Data is immediately applied to `buildQuestionSet()` in `math.js` via `state.settings`.

#### Category 4: Visual Design

15. **Does the settings panel look clean and professional?** 2/5
    The `.parent-panel` CSS block (white card, border, shadow) is defined but the section element uses `class="screen screen--parent-panel"` so the card styles never render. The dynamically generated `<h3>` headings have no CSS class — they render in browser-default heading font, inconsistent with the game's Nunito weight-900 style. Individual `.parent-setting` rows, `.btn` buttons, and `.badge-list` items are styled, but the overall impression without the card wrapper is a bare developer view.

16. **Is the visual style consistent with the rest of the game?** 3/5
    `.parent-panel__title` has correct CSS (purple, weight 900). The PIN screen has a defined purple-themed look. `.btn` variants, `.parent-setting` rows, and badge chips all use the game's design tokens. However, the missing card container and unstyled `<h3>` headings create inconsistency with the polished child-facing screens.

17. **Is the settings panel visually distinct from the child's game screens?** 3/5
    The PIN screen `screen--parent-pin` is partially distinct (purple elements within it), but its `.parent-pin` container CSS never fires because the section class doesn't match. The settings panel itself has no distinguishing background or border — once a parent unlocks it, the screen looks very similar to an unstyled game screen. A child who wanders back to an open settings screen would not clearly understand they are in a parent-only zone.

18. **Are interactive elements (buttons, toggles, sliders) visually clear?** 3/5
    `.btn` and `.pin-key` buttons have clearly visible press states. The `.parent-setting__select` dropdowns are styled with borders and shadows. The sound checkbox is an unstyled native `<input>` — small default iOS system checkbox on Safari iPad, inconsistent with the rest of the panel. The 🔒 header gate button has no CSS affordance.

#### Category 5: Functionality

19. **Are settings saved to localStorage immediately and reliably?** 4/5
    Every mutation function — `setOperationEnabled`, `setOperationLevel`, `setSoundEnabled`, `changePin`, `resetProgress` — calls `saveState()` synchronously. `loadState()` on boot calls `hydrateState()` and settings are applied immediately. The `change` event delegation in `initParentPanel()` fires for all relevant inputs. Minor deduction: the `change` handler does not show any error feedback if `setOperationEnabled()` returns `{ ok: false }` (when trying to disable the last operation).

20. **Does the parent receive visual confirmation that settings were saved?** 2/5
    No in-game toast or visual signal when a toggle or dropdown changes. Reset uses `window.alert('Voortgang gewist.')` and PIN change uses `window.alert('Pincode gewijzigd.')` — these communicate success but are native browser dialogs. A parent toggling sound or changing a level gets zero feedback that the change was persisted.

21. **Are saved settings correctly applied during gameplay?** 4/5
    `buildQuestionSet()` in `math.js` reads `state.settings.operationLevels[operationId]` and selects the matching level config for number ranges and difficulty. `renderOperationCards()` disables cards for operations not in `state.settings.enabledOperations`. Sound checks `state.settings.soundEnabled` in `sounds.js`. Settings flow correctly from parent panel → state → gameplay. Deducted one point because the missing "problem type" setting means the parent cannot switch to visual-counting mode.

22. **Does the reset progress function work completely and correctly?** 4/5
    `resetProgress()` resets all progress fields and build state; `saveState()` is called; settings are preserved. Deducted one point: `renderParentPanel()` is not called after reset, so the badge list remains visually stale until navigation. The panel should call `renderParentPanel()` at the end of the reset flow.

### Top 5 Issues

1. **No parent-facing progress summary**
   - **What:** The parent panel still shows only a badge list. All meaningful progress data (`totalCorrect`, `bestStreak`, `earnedBlocks`, `earnedStickers`, `completedBuilds`) exists in state and is displayed on the child's `screen-progress`, but none appears in the parent panel.
   - **Why it matters:** A parent coming back to settings after a week cannot quickly assess how the child is progressing. The child's progress screen is not PIN-protected and is not linked from the parent panel.
   - **Where:** `scripts/main.js` → `renderParentPanel()` (~line 869); data available in `scripts/state.js` `state.progress` and `state.builds`
   - **Severity:** Critical

2. **`.parent-panel` CSS card class never applied**
   - **What:** `styles.css` defines a polished card under `.parent-panel` (white bg, max-width 760 px, purple border, box-shadow). The `<section id="screen-parent-panel">` uses `class="screen screen--parent-panel"`, not `parent-panel`. The `data-settings-content` div uses `class="parent-panel__body"`, also without CSS. None of the card styles render.
   - **Why it matters:** The settings panel looks like an unstyled debug form. First impression significantly undermines trust.
   - **Where:** `index.html` line 564 (section class); `styles/styles.css` `.parent-panel` block (~line 1620)
   - **Severity:** High

3. **Missing required settings: max number range and problem type**
   - **What:** No slider or input to cap the number range below level 1 (e.g., for a child struggling with sums above 5). No selector for numeric vs. visual-counting problem format. Three difficulty levels per operation are available but are not granular enough to replace a proper max-number control.
   - **Why it matters:** A parent cannot fully personalise the difficulty for their specific child. This is listed as required in the project spec.
   - **Where:** `scripts/main.js` → `renderParentPanel()`; `scripts/math.js` → `buildQuestionSet()`; `scripts/state.js` → `defaultSettings()`
   - **Severity:** High

4. **No save confirmation feedback after setting changes**
   - **What:** Toggling an operation, changing a level, or switching sound saves silently via `initParentPanel()`'s `change` handler. No toast, checkmark, or visual change signals success.
   - **Why it matters:** A parent in a hurry taps a setting and immediately closes the panel. With no feedback, they cannot be sure the change was stored.
   - **Where:** `scripts/parent-settings.js` → `initParentPanel()` (~line 170); no confirmation UI anywhere.
   - **Severity:** Medium

5. **Native browser dialogs for reset and PIN change**
   - **What:** Reset uses `window.confirm` + `window.alert`. PIN change uses `window.prompt` + `window.alert`. These are unstyled OS-level dialogs — jarring in a polished game context, not optimised for iPad touch, and `window.prompt` provides no real-time 4-digit validation.
   - **Where:** `scripts/parent-settings.js` lines ~182–207
   - **Severity:** Medium

### Quick Wins

- `index.html` line ~575: Add `parent-panel` to class list of `data-settings-content` div — one word, instant card styling.
- `main.js` `renderParentPanel()`: 3-line change to apply `.toggle` wrapper to sound checkbox.
- `main.js` `renderParentPanel()`: Add a `<div class="parent-setting progress-summary">` with 4 stat chips before the operations list.
- `parent-settings.js` `initParentPanel()`: After `resetProgress()`, call `document.getElementById('screen-parent-panel') && renderParentPanel?.()` to refresh stale badge list.
- `styles.css`: Add `.app-header__parent-btn` with a small purple pill or circular background to give the lock button a visual affordance in the orange header.

---

### Risky Changes

- **Replacing `window.confirm/alert/prompt` with in-game dialogs** requires building a modal. Reusing or extending the existing `reward-modal` risks breaking the reward flow if not cleanly separated.
- **Adding max-number and problem-type settings** requires changes across `math.js`, `state.js` (new fields), `storage.js` (schema migration to v3), and `parent-settings.js`. A missed migration will silently break settings for returning users.
- **Default PIN change** from `1234` to a randomly generated code on first boot requires special logic in `hydrateState()` and must handle the case where `parentPin` already exists in localStorage.

### Verdict

**Almost there** (overall score 3.2 / 5)

A parent can find the settings, enter the PIN, toggle operations on and off, and change difficulty levels — the fundamental plumbing works. But the same two-word summary from Review 1 still applies: the panel looks unfinished and it tells a parent nothing about how their child is actually doing. The CSS card mismatch means the polished visual design intended by the stylesheet never renders. None of the five issues flagged in Review 1 have been addressed; all Quick Wins remain available. Implementing improvements 1 and 2 together (progress summary + CSS card fix) would be the single most impactful pair of changes, likely lifting the overall score to 3.8–4.0.
